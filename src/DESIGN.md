# Versioned filesystem cache

`versionedCache.cts` binds the logical `serverDistDir`, installed Next filesystem-cache constructor and immutable artifact namespace before `plugin.ts` prepares the production server. Rebinding a different artifact in one worker and changing a build during prepare both fail startup. No request re-resolves a build identity or constructor from the replaceable app path. The native CJS registry bridges Harper's VM plugin and Next's native CJS handler, including separate package copies.

`VersionedCacheHandler.cts` writes through the captured runtime delegate. A whole-entry miss can use a second delegate whose filesystem cannot write or read legacy `server/route-cache`. Per-file fallback could mix runtime HTML with seed RSC. Seed reads still use the component pathname; this is cache-write isolation, not arbitrary application-file read isolation.

A native cache null can mean tag invalidation, not only missing files. Before any disk-backed runtime write, the handler persists key ownership under `entries/{fetch,render}/<key-hash>` in its namespace. A null for an owned key stays null, including after worker restart or a partial/failed write; it never revives an older seed whose tags differ. Marker failure prevents the runtime write. An unreadable marker counts as owned: the read misses so Next re-renders, rather than failing the request or falling back to a seed. Separate fetch/render key spaces avoid collisions between Next's data-cache hashes and route names. Memory-only writes do not create disk markers, and seed delegates preserve the caller's flush setting. This is worker-restart persistence with Next's unsynced filesystem behavior, not fsync-ordered power-loss durability; losing ownership during host failure can permit a same-build seed, without crossing artifact namespaces.

The artifact digest includes build seeds, manifests, compiled server files and Next package metadata; it excludes the legacy route-cache directory. These build files stay immutable when this handler owns runtime writes, so restart identity is stable. This also handles a reused BUILD_ID; Next15/16 preview IDs alone would not, because they can be cached across builds. Outgoing stock workers can mutate render seeds on 14/15/16.2 and fetch seeds on every supported version, so the initial migration stops them before replacing the app.

Artifact hashing reads bounded chunks asynchronously before serving and after prepare; it yields between file operations and never runs from a request or cleanup timer. The installed Next constructor is captured before hashing; package metadata uses Node resolution to support a hoisted Next installation.

The cache root resolves existing ancestors through `realpath` before directory creation; both its configured and physical paths must be outside the component, must not contain it, and must not sit inside `components/`, because namespace directories there would be loaded by Harper as components. Capturing that physical root prevents later alias retargeting from redirecting worker writes. Missing descendants remain supported; other filesystem errors propagate at startup.

Namespaces and ownership markers are retained for operator-managed cleanup after their workers stop. No automatic cache sweep is added: a pre-delete liveness check cannot exclude a concurrent activation, and removing ownership markers while a worker serves can revive older seeds after invalidation.

`VersionedCacheHandler.test.ts` exercises installed Next14/15/16 caches against real files and fresh processes. `integrationTests/next-16-versioned-cache.pw.ts` holds a real regeneration across the swap and verifies the new build and persistence after restarts.

# Reload on a missing server action

`actionReload.ts` turns Next.js 16's missing-action response into a full page load of the current page. Next.js answers an action ID the build doesn't have with `x-nextjs-action-not-found: 1`, and its client throws `UnrecognizedActionError`. `plugin.ts` wraps the response's `setHeader` on fetch-action POSTs only; when Next.js sets that exact marker, the wrapper sets `x-action-redirect: <page>;replace` instead and keeps Next's status and body. The Next.js 16 client rejects the action with a redirect error and does a hard navigation. The action never ran, so the reload loses only client state.

It runs on Next.js 16 production servers only. Next.js 15's client resolves the action with `undefined` before navigating, so code after `await action()` would run as if the action had succeeded. That also means a tab still running a Next.js 15 client when the server is upgraded to 16 gets that behavior once. Dev mode is excluded, and `reloadOnMissingAction: false` turns it off.

The redirect target is the request path: origin-relative only, with `basePath` removed because the client's `assignLocation` adds it back, and `;` escaped because the client splits the header on `;`. Anything else, or any error while setting the headers, leaves Next's own response in place.

The guard cookie (`__harper_nextjs_action_reload`, 30 seconds) bounds reloads for sequential requests from a browser that accepts cookies: the request after a reload carries it and gets Next's error. Requests already in flight before the cookie lands can each reload once, and a browser that rejects cookies reloads on every miss, so an action called on mount that always misses can loop there. The suppressed path never refreshes the cookie. The guard is appended to any `Set-Cookie` already on the response.

`actionReload.test.ts` covers the wrapper on fakes and on real HTTP/1 and HTTP/2 responses. `integrationTests/server-action-skew.pw.ts` keeps an old tab open across a rebuild and a renamed action, checks the opt-out, and shows the guard stopping a second reload between nodes that disagree on action IDs.
